## 原始归档独立复核

对提交 `48c0045` 的完整运动归档再次核验 SHA-256，并逐字段比较三段 BIN 与 CSV，全部 2,744 条记录一致。重新执行分析器，主要结果与归档 JSON 一致；另外用独立的二进制字段解析、DWT 回绕处理和梯形积分回归复算了参考/反馈积分比例。归档运动 ELF 的 SHA-256 也与运行元数据一致。当前诊断主机测试 9/9 通过。

### 相位：参考发布约 2 ms，电机参考到反馈约 6 ms

把 Cmd 发布的参考与电机控制回调实际使用的参考分别按各自 DWT 时间戳对齐后，两段动态数据均得到：

| 比较 | 阶跃 | 平滑 |
| --- | ---: | ---: |
| 电机使用的参考相对 Cmd 发布参考滞后 | +2 ms | +2 ms |
| 反馈位置相对电机使用的参考滞后 | +6 ms | +6 ms |

这与直接比较 Cmd 参考和反馈得到的约 8 ms 滞后相符。这些是波形拟合值，不是独立测得的物理延迟：其中仍混有任务调度、反馈接收年龄和机械响应，不能将 6 ms 全部归因于电机滤波。每条记录中的电机快照在该次 Cmd 开始之前约 0.055–0.425 ms 产生，因此不能把两份快照视为同一次控制计算。

本次数据支持 JOINT1 的参考位置与速度一致、平均 Cmd 频率约 500 Hz；没有复现原 JOINT2 截图中的位置超前或约 0.765 的参考积分比例。两轴控制配置不同：JOINT1 的发送组为 500 Hz、外层 Kp=6、MIT Kp/Kd=0/35；JOINT2 的发送组为 250 Hz、外层 Kp=4、MIT Kp/Kd=10/50，见 [ARX-X5 配置](../profiles/arx_x5.c)。因此，本次不能判定历史 JOINT2 异常的根因，也不支持按 0.765 修正前馈倍率。要关闭该问题，仍需 JOINT2 在原问题工况下的同类同步采样。

### 已确认的问题：误差不变时 D 项保留旧值

[PID_Calc](../../libs/controller/pid.c) 在 `|error[0] - error[1]| <= 1e-6` 时，仅当旧的 `|d_error| < 0.001` 才更新 `d_error`。旧值达到该阈值时，误差即使完全不变，D 项也不会归零。

在阶跃段 1,239 对相邻电机样本中，**124 对**满足“误差完全相等，但 `|d_error| >= 0.001`”。保持和平滑段未出现这一条件。一个具体样本如下：

| 字段 | 数值 |
| --- | ---: |
| `motor_seq` | 26910 |
| 电机参考 / 反馈位置 | 44.180366516° / 44.074516296° |
| 本次 / 上次位置误差 | 0.105850220° / 0.105850220° |
| 当前误差差分 | 0° |
| 实际保留的 `d_error` | 0.021869659° |
| `Kd * d_error` | **+1.093482971°/s** |

用仓库现有 `pid.c` 在主机直接调用 `PID_Calc` 也复现了这一行为：Kp/Kd=6/50，先让误差从 0.083980560° 变为 0.105850220°，再保持相同 ref/fdb 调用一次，第二次的 D 项仍为 +1.093482971°/s。实机中也出现负向旧值被保留。这解释了阶跃平台期部分不应持续的 D 项补偿，是独立于 Ruckig 的控制器问题；它不能证明历史 JOINT2 的大幅相位异常由此造成。本次复核仅记录该问题，未修改控制算法。

### CPU 数据的适用范围

归档编译命令确认 Ruckig 与控制代码均为 `-O0`。两次运行元数据的 `SCB.CCR` 均为 `262656`（`0x40200`），I-cache、D-cache 使能位均为 0；位定义见 [CMSIS Cortex-M7 头文件](../../Drivers/CMSIS/Include/core_cm7.h)。因此，前述 28.296 µs / 406.419 µs 是本次 Debug、缓存关闭工况下的缓存采样 / 强制重规划耗时，不能直接当成优化构建的性能。

按原始样本的 `new_calculation` 标志，阶跃段重规划为 3/1,240 次，平滑段为 210/1,238 次。仅将这两个比例代入 STOP 基准的平均耗时，加权估计得到单轴约 **29.21 µs（500 Hz 的 1.46%）** 和 **92.44 µs（4.62%）**。这不是运动期间求解器实际 CPU 时间的测量：实际规划输入会影响求解耗时，而且 Cmd wall time 还包含其他控制工作和任务抢占。不能用整段 Cmd wall time 代替 Ruckig 的 CPU 占比。
