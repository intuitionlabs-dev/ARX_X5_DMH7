# 关节插值 CPU 对比

在 Linux 主机上分别编译并运行 `rebuild` 的五次插值和当前分支的 Ruckig。
两次构建均调用各自提交中真实的 `Arm_Ref_Set()` 普通位置路径，包含六轴参考选择、
轨迹计算及结果发布。没有重新实现五次插值，也不调用电机。

```bash
python3 scripts/benchmark_joint_interpolation.py \
  --cycles 200000 --rounds 7 --warmup 5000 --cpu 0 \
  --output-dir build/interpolation-benchmark
```

需要 Git、CMake、C/C++17 编译器。可用 `--cmake /path/to/cmake` 指定工具。
输出目录必须没有已有源码快照；重测时换一个 `--output-dir`。
默认对照提交为 `3317d9b9dbe7afa5f0b0b182fe44cf94a8752ec7`，Ruckig 版本为 `HEAD`。
未提交的生产代码不参与测试；`--baseline`、`--current` 可指定其他兼容提交。

额外比较单精度和原双精度内核：

```bash
python3 scripts/benchmark_joint_interpolation.py \
  --double-ref 730d165 --current f0689c9 \
  --cycles 200000 --rounds 7 --warmup 5000 --cpu 0 \
  --output-dir build/interpolation-float-benchmark
```

这会在同一次测试中轮换运行五次插值、双精度和单精度 Ruckig；原双精度提交
`730d165` 与单精度提交 `f0689c9` 均被重新编译。元数据额外记录标量字节数及
每轴上下文大小。目标生成和校验和仍使用相同的原始基准实现（计时范围之外），
以保证三组输入完全一致；Ruckig 单精度求解路径不含双精度运算。

## 测量范围与计算

- 两边均使用 `-Os`，关闭 LTO，不使用 fast-math；优化等级与固件 Release 一致。
- 同一线程固定到一个 CPU，轮流先运行五次插值或 Ruckig，共 7 轮。
- 每轮预热 5,000 周期后测量 200,000 周期；创建、预热、目标生成、校验及释放不计时。
- 使用 `CLOCK_THREAD_CPUTIME_ID` 计算线程 CPU 时间；另存单调时钟耗时用于观察调度干扰。
- 计时包含相同的目标数组复制和循环开销，不包含 TD、动力学、通信、RTOS 或其他任务。
- 检查规划器未进入失败回退，且最终输出为有限值；出错则不报告有效测量。

```text
平均每周期 CPU 时间 = 计时段线程 CPU 时间 / 周期数
500 Hz 下的单核占比 = 平均每周期 CPU 时间 / 2000 µs × 100%
新增占用（百分点） = Ruckig 占比 − 原五次插值占比
```

双臂计时包含两台臂的十二轴，一周期仍是 2 ms。
这是按控制周期折算的计算负载：基准程序自身连续运行，没有每周期 sleep，
因此进程监控工具显示的运行期间 CPU 百分比与这里的折算值不同。
采用线程 CPU 时间可排除进程未被调度的等待，结果仍受 CPU 架构、频率和虚拟化影响。

## 场景

| 场景 | 输入 |
| --- | --- |
| `settled` | 已到达零目标，之后保持目标不变 |
| `step_1hz` | 每秒改变一次各关节目标，幅度 10～20° |
| `smooth_100hz` | 100 Hz 更新正弦位置目标，500 Hz 执行参考计算 |
| `smooth_500hz` | 每个控制周期都更新正弦目标，六轴频率各不相同 |
| `random_500hz` | 每个周期更新 ±60° 范围的确定性伪随机目标，作为突变压力输入 |

每个场景分别测单臂和双臂。同一场景两种算法使用完全相同的目标序列。
两者轨迹结果不相同：五次插值固定时长 0.16 s；Ruckig 最短时长 0.16 s，
并限制速度 90°/s、加速度 360°/s²、加加速度 3600°/s³。
场景平均值与多轮最大平均值均不代表单周期最坏执行时间。

## 输出

`raw.csv` 保存每轮线程 CPU 时间、单调时钟时间、周期数和结果校验和。
`summary.csv` 保存各场景的多轮均值、标准差、最小／最大轮均值、占比及新增百分点。
`metadata.json` 保存实际提交号、编译器、CPU 信息、测试源码哈希和采样设置。
源码快照、实际编译命令及可执行文件一并保留在输出目录。

## 2026-11-04 全单精度对比

在同一台 AMD EPYC-Milan x86_64 虚拟机上，固定 CPU 0，GCC 15.2.0、`-Os`，
同时重跑五次插值 `3317d9b`、双精度 Ruckig `730d165`、单精度 Ruckig `f0689c9`。
基准脚本及程序版本为 `2c54d1c`；具体哈希见元数据。每场景 7 轮，每轮 200,000 周期，
预热 5,000 周期。总计 210 次测量、4,200 万个计时周期，无规划失败，各组校验和重复一致。
以下 CPU 占比均为参考计算平均耗时除以 2 ms 后折算的单核占比。

| 臂数 | 场景 | 五次耗时 µs | 双精度耗时 µs | 单精度耗时 µs | 五次 CPU | 双精度 CPU | 单精度 CPU | 单精度耗时减少 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 目标保持 | 0.021 | 0.226 | 0.201 | 0.0010% | 0.0113% | 0.0100% | 10.89% |
| 1 | 1 Hz 阶跃 | 0.030 | 0.248 | 0.230 | 0.0015% | 0.0124% | 0.0115% | 7.19% |
| 1 | 100 Hz 平滑目标 | 0.186 | 1.674 | 1.461 | 0.0093% | 0.0837% | 0.0730% | 12.76% |
| 1 | 500 Hz 平滑目标 | 0.576 | 7.090 | 6.812 | 0.0288% | 0.3545% | 0.3406% | 3.92% |
| 1 | 500 Hz 随机目标 | 0.564 | 2.238 | 2.246 | 0.0282% | 0.1119% | 0.1123% | -0.36% |
| 2 | 目标保持 | 0.041 | 0.453 | 0.407 | 0.0020% | 0.0227% | 0.0203% | 10.32% |
| 2 | 1 Hz 阶跃 | 0.060 | 0.508 | 0.462 | 0.0030% | 0.0254% | 0.0231% | 9.04% |
| 2 | 100 Hz 平滑目标 | 0.342 | 3.145 | 2.932 | 0.0171% | 0.1572% | 0.1466% | 6.76% |
| 2 | 500 Hz 平滑目标 | 1.180 | 14.385 | 13.208 | 0.0590% | 0.7192% | 0.6604% | 8.18% |
| 2 | 500 Hz 随机目标 | 1.131 | 4.791 | 4.784 | 0.0566% | 0.2396% | 0.2392% | 0.15% |

双臂高频平滑输入下，单精度比双精度少用 1.177 µs／周期（8.18%），
相对五次插值仍增加 12.028 µs／周期，即 0.6014 个 CPU 百分点。
该场景单精度 7 轮均值范围为 12.895～13.464 µs，标准差 0.176 µs；
双精度范围为 14.009～15.217 µs，标准差 0.440 µs。
随机输入的差异很小，单臂甚至略慢；不能据此声称所有场景都有稳定加速。
这次比较包含单精度移植所需的数值判定与整数采样计数改动，不是只改变寄存器数据宽度的实验。

主机每轴上下文由 **3664 B → 2224 B**，减少 **39.30%**（不含分配器开销）；
十二轴合计减少 17,280 B。H7 单精度每轴上下文为 1880 B，ABI／指针宽度不同，
不要把主机结构大小直接用于 MCU 堆空间计算。C 接口已改为 `float`，旧调用端必须重新编译。

验证：165 项回归测试通过；独立 C API 测试新增 738 万次单轴更新，检查有限值、速度、加速度、
jerk 和相邻采样位移约束，并包含小系数、反向相消和极短正时长的精确失败用例回归。
误差阈值按 FP32 舍入量级调整，不能与原双精度的绝对精度保证等同。ASan／UBSan／泄漏检查通过；
H7 Release 和混合机型 Debug 构建通过；ARM 库没有双精度数学符号、运行时辅助函数或 `.f64` 指令。

**这些数据不是 H7 实测，也不是整机 CPU 占用率或最坏执行时间。** 本次未连接硬件，不能按主频比例换算。

## H7 实机测量

板上测试入口为 [h7_joint_benchmark.c](../../App/test/h7_joint_benchmark.c)，
公共工作负载和统计在 [joint_benchmark.c](../../App/test/joint_benchmark.c)。
默认关闭，通过独立构建目录启用：

```bash
cmake -S . -B build/H7-joint-benchmark -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake \
  -DCMAKE_BUILD_TYPE=Release -DH7_JOINT_BENCHMARK=ON
cmake --build build/H7-joint-benchmark -j4
```

需要完整 ARM GCC C/C++17 工具链、CMake、Ninja，以及本项目构建所需的 Python。
生成 `build/H7-joint-benchmark/CtrBoard-H7_ALL.elf`，用现有 SWD 下载工具烧录。
若需要二进制文件：

```bash
arm-none-eabi-objcopy -O binary \
  build/H7-joint-benchmark/CtrBoard-H7_ALL.elf \
  build/H7-joint-benchmark/CtrBoard-H7_ALL.bin
```

这是专用测试固件。启动后在 `SystemClock_Config()` 后进入独立的 16 KiB 栈测试任务，
初始化 GPIO、DMA 和 USART1，跳过正常 BSP、FDCAN、机器人协议、遥控和电机任务初始化。
测试使用内存中的模拟机械臂，不发送电机控制指令。完成后保留结果并退出测试任务，
不会继续进入机器人程序。恢复控制功能时烧录 `H7_JOINT_BENCHMARK=OFF` 的正常固件。

### 连接及运行

1. 板上 **USART1 TX（PA9）→ USB-TTL RX**，并连接 GND；使用 3.3 V TTL。
   本测试只输出，PA10 不需要连接。该接口不是 USB CDC 或 USART3 RS485。
2. 串口设为 **921600 baud、8N1、无流控**，打开日志保存，再复位板子。
3. 等待 `meta,...`、表头及各行 `case,...`，最后收到 `done,...`。
   默认测试单臂 6 轴、双臂 12 轴，各 5 个场景，两种算法、3 轮，共 **60 行结果**。
4. `done` 中 `failed=0`、`uart_errors=0` 且所有行 `error=0` 才表示本轮有效。
   若有求解失败或样本不完整，不要把部分轨迹或失败回退的耗时当作正常性能。

也可以不接串口，用 SWD 调试器查看全局变量 `h7_joint_benchmark`。
测试固件保留调试信息，Release 仍按 `-Os` 优化。让 MCU 连续运行，待 `state=2`
后再暂停查看 `results`；测量中不要单步、设断点或频繁读内存。复位可重新测试。

| 观测字段 | 含义 |
| --- | --- |
| `state` | 0 未开始，1 运行中，2 已结束；负值是启动失败 |
| `active_result` / `active_tick` | 当前结果索引／周期，含预热周期 |
| `completed` / `failed_cases` | 已完成／失败的用例数 |
| `core_hz` / `irq_masked` | 实际 `SystemCoreClock`／是否在计时区间屏蔽中断 |
| `icache_enabled` / `dcache_enabled` | 进入测试时的缓存状态；测试不主动修改缓存配置 |
| `counter_overhead_cycles` | 64 次空测量中的最小开销；原始结果不扣除该值 |
| `stack_free_bytes` | 测试任务栈历史最小剩余空间，单位字节 |
| `results[i].stats` | 总周期数、样本数、最小／最大周期、平均／峰值时间与 CPU 占比 |

启动错误：`-10` 时钟无效，`-11` DWT 计数器不可用，`-12` 任务创建失败，`-13` 内核启动失败。
用例错误：`-20` 上下文分配失败，`-21` 计数为零或单次测量超过一秒；其他负值表示
规划／输出校验失败，其中 Ruckig 求解错误沿用 C 接口返回码。`error_tick` 是失败周期，
从 0 起且包含预热；成功时为 `UINT32_MAX`。

### 测量范围

Ruckig 路径通过测试专用入口调用生产代码 `Arm_Ref_Set()`。
五次插值对照来自 `rebuild` 的 `3317d9b`，保存在
[joint_quintic_baseline.inc](../../App/test/joint_quintic_baseline.inc)：保留参考选择、
重规划和样条计算逻辑，仅适配状态存储及原先的 0.16 s 配置值。
两个算法在同一固件、同一时钟、同一场景中轮换运行，重置到相同初态和随机种子。
本测试比较 **五次插值和当前单精度 Ruckig**，不包含双精度 Ruckig。

每次计时包含该周期内所有臂的目标复制、参考选择、插值及结果写入，不含目标生成、
创建／释放、校验、串口输出、动力学和通信。五种场景含义与主机测试一致，板上目标
生成采用 `sinf` 和单精度常量，因此不能要求它与主机原先双精度生成的输入逐位一致；
板上两种算法的输入完全相同。

每个用例默认预热 1,000 周期，再测 10,000 周期。模拟控制时间每次推进 2 ms，
程序连续计算、每 128 次在计时区间外让出一次 CPU，**并不每周期等待 2 ms**。
这里的 CPU 占比表示这段参考计算在 500 Hz 调用频率下占用的预算，不是测试任务在
连续跑分期间的 RTOS 使用率，更不是整机总 CPU 占用率。

DWT `CYCCNT` 每次采样用无符号 32 位差值处理回绕，再用 64 位累计总周期数。
每次计时应小于一次完整计数器回绕，代码另外拒绝超过一秒的单次样本。
测量前后使用屏障，保留读计数器和循环／调用开销，不扣除空测量值。
`SystemCoreClockUpdate()` 后的内核时钟用于转换；不要在测试中途修改时钟。

```text
total_cycles = (total_hi << 32) | total_lo
mean_us = total_cycles / samples / core_hz × 1,000,000
cpu_percent = mean_us / 2000 × 100
max_us = max_cycles / core_hz × 1,000,000
新增占用（百分点） = Ruckig cpu_percent − quintic cpu_percent
```

CSV 的 `total_hi`、`total_lo` 是总周期数高／低 32 位十进制整数，避免依赖 nano printf
的 64 位格式支持。`mean_us`、`cpu_percent`、`max_us` 已在板上计算并输出，
`over_budget` 为单次参考计算 **超过 2 ms** 的次数，`checksum_bits` 为最终输出
校验和的 FP32 位模式（十六进制）。同算法、同臂数、同场景的多轮校验和应一致。
单周期观测峰值不等于所有输入和完整系统条件下的最坏执行时间保证。

### 可选配置

以下参数在 CMake 配置时指定，默认值如下：

```bash
-DH7_JOINT_BENCHMARK_SAMPLES=10000
-DH7_JOINT_BENCHMARK_WARMUP=1000
-DH7_JOINT_BENCHMARK_ROUNDS=3
-DH7_JOINT_BENCHMARK_MASK_IRQ=ON
```

样本数和预热数范围为 1～1,000,000，轮数为 1～10。默认仅在单次测量时用 PRIMASK
屏蔽可屏蔽中断，采样后恢复原状态，用于测算法自身开销；串口、目标生成和校验时不屏蔽。
设为 `OFF` 可观测包含中断抢占的耗时，但此时仍是专用测试固件，没有正常电机和通信任务负载。
对比两次结果时保持优化等级、时钟、缓存及中断设置一致。`meta` 行会记录实际参数。

当前验证：专用 Release（屏蔽／允许中断）和普通 Release 构建通过，166 项回归测试通过。
原生测试覆盖相同输入、重复性、失败检测、计数回绕、64 位累计及 CPU 占比公式。
链接符号检查确认专用固件没有正常 CAN 初始化／电机任务入口，普通固件没有测试入口。
